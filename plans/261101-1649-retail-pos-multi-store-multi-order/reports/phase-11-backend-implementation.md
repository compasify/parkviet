# Phase 11 backend: kill-switches, operational metrics, security and fault suites

Status: implemented, not committed. Phase status cells were not edited.

## Contract for the frontend

- `GET /api/v3/admin/pos/context[?branch_id=]` now has `features`: `{ credit, returns, refunds, exchanges, traceability, customer_display, cash_moves, exports }` (booleans) for the selected branch; without a branch, the store defaults. The server refuses a disabled command on its own (`409`, `error.details.reason = "feature_disabled"`, `error.details.feature = "<name>"`), so the UI flag is only a hint.
- Management (not in the original contract, needed to switch flags and for the audit):
  - `GET /pos/feature_flags[?branch_id=]` → `{ data: { branch_id, features (effective), switches: { <feature>: { store, branch_override (false|null), effective } }, settings: [{ feature, enabled, branch_id, reason, changed_by_id, changed_by_name, changed_at }] } }`. Readers: `read_pos_topology`, `write_pos_topology`, or `pos.topology.manage` at that branch (not at another branch).
  - `PUT /pos/feature_flags/:feature` body `{ branch_id?, enabled, reason }`. **Effective value = store default AND branch override** (see "Sửa sau review"). Without `branch_id`: store default `true|false`, needs `write_pos_topology`. With `branch_id`: `false` switches that branch off (`write_pos_topology` or `pos.topology.manage` at that branch); `true` or `null` drop the override (= follow the store default) and need `write_pos_topology`. Reason required (≤ 200). Authority is checked before input. Errors: `409` reasons `reason_required`, `reason_invalid`, `feature_unknown`, `feature_value_invalid`; `403` without the right; `404` for another store's branch. Returns the effective switches.
- `GET /pos/operations/metrics?branch_id=` (APPROVE or `pos.report.read` at the branch, else 404; `Cache-Control: no-store`) → `data`: `tenders {prepared, unknown, oldest_unresolved_age_seconds}`, `outbox {pending, failed, oldest_pending_age_seconds}` (store-wide; `null` unless the reader holds `write_pos_topology`), `attention {stale_tenders, completion_pending, stale_refunds, stale_liability_payouts, returns_awaiting_predecessor, stale_returns, open_stock_discrepancies, funds_needing_attention}`, `variances {counts_awaiting_close, closures_with_unexplained_variance (last 30 days), held_cash_unreconciled, cash_requests_pending}`, `payouts {refunds: {status: count}, liability_payouts: {status: count}}`, `traceability {enrolled, drifted, last_checked_at}`, `lock_waits {available, waiting, oldest_waiting_statement_seconds}` (database-wide), plus `generated_at`, `stale_after_seconds` (900, same threshold as the recovery sweeps), `variance_window_days` (30).

## Flag semantics per feature

Every feature is off until a store manager turns the store default on (no row = off); a branch override can only switch a branch off. Off refuses only a *new* command of the feature, inside the command executor after the replay check, so replaying an already executed command with the same key still returns its stored result. Turning a feature off or on never deletes or rewrites attempts, receipts, ledger, stock or audit rows (spec compares ids and `updated_at` of ten ledgers across 16 switches). Every real change writes one `feature_flag.change` audit entry (`scope`, `from`, `to`, `reason`, `branch_id`); setting the same value again writes nothing.

| Feature | Off refuses | Still allowed |
|---|---|---|
| credit | credit request, credit approval (direct or answering a request), completion with `credit_approval_id` (the refused completion releases the reservation and revokes its approval, reason `feature_disabled`) | paid sales, credit reject/revoke/release, credit account configuration, collections and their allocations/reversals of existing debt, receivables reads |
| returns | `Returns::Prepare` (new return) | preview (read-only), approve, receive, cancel of returns already prepared; the recovery job posting waiting entitlements |
| refunds | `Refunds::Request` (new refund reservation) | approve, confirm payout, resolve of requests already made; liability payouts of unallocated funds (decided: they are the recovery path for money that should not have been taken, so they stay open) |
| exchanges | `Exchanges::Execute` | the replacement workspace already created is an ordinary sale |
| traceability | opening balance (enrollment, branch effective value) and switching a SKU's `tracked_mode` to serial/lot (store-wide setting, so the store default decides) | selling, reserving, handing over and returning tracked goods; receipts, transfers, counts, quarantine and recall of stock already tracked (blocking them would drift typed stock from the shelf) |
| customer_display | bind/rebind, pin, issuing and exchanging pairing codes (codes still open are spent when the feature goes off) | clear, revoke, display state reads and ACK (so a pinned screen can still be cleared) |
| cash_moves | new cash in, cash out and safe drop requests | confirm or cancel of requests already made; shift count/close; late-cash reconciliation |
| exports | creating an export | download links of existing exports, reports |

Always open regardless of flags: receipt lookups/prints, command receipts, tender cancel and settlement recovery, liability payout confirm/resolve, shift close, reconciliation, reports, metrics.

Spec setup: `spec/support/pos_feature_helpers.rb` (required once from `rails_helper.rb`) turns every feature's store default on for the store of each branch created in a spec (rows inserted directly, no audit, purged with committed rows); examples about the switches use `pos_features: :default`.

## Observability

`CommandExecutor` writes one JSON line per command under the `pos command` log tags: `event: pos.command`, `command`, `outcome` (`executed`, `replayed`, `conflict`, `feature_disabled`, `refused`, `error`), `reason` (conflict reason or error class), `store`, `branch`, `workspace`, `actor` (prefixed ids), `key_digest` (first 16 hex of an HMAC-SHA256 of the idempotency key, secret derived from `Rails.application.key_generator`), `parent` (the outer command when run inside another command's transaction), `duration_ms`. `branch` is logged only when it belongs to the store. Never the key, payload values, tokens, amounts or names (spec checks a key and note containing a phone number never reach the log). Logging failures are swallowed so they never affect a command.

## Defects found and fixed

1. **Case-of-24 prices were refused** (`unit_normalizer.rb`): `BigDecimal * Rational(1, 24)` rounds to a repeating decimal, so a correctly configured `thùng 24 chai` at 240,000 failed with "Price cannot be represented exactly per base unit" (I01). The per-base price is now computed in `Rational` and returned as an exact `BigDecimal`; unrepresentable prices (250,000 / 24) are still refused. Regression expectations added.

No other defect surfaced; nothing needed a product decision.

## Sửa sau review

Decision applied (coordinator): effective value = store default AND branch override. A branch row is only ever stored as `enabled: false`; `true` or `null` for a branch both drop the override (simpler than refusing `true`). Branch topology managers may only switch their own branch off; turning anything on (store default, or dropping a branch override) needs `write_pos_topology`.

1. **Precedence** (`feature_policy.rb` rewritten, `feature_flags_controller.rb`): `for_branch`/`enabled?` = store AND NOT branch-off; `describe` gives `{store, branch_override, effective}` per feature for the list endpoint (`switches`); context `features` use the same rule. `set!` authorizes before validating input. Specs: store off + branch "on" → off (and no row stored); branch override off wins; branch manager can switch own branch off, gets 403 for on/null and for the store default; manager of branch A gets 403/404 reading or setting branch B and the store list.
2. **Exact quantity normalisation** (`unit_normalizer.rb`): the unit factor is a `Rational` (was `BigDecimal`, so `3 kg` at ratio 1/3 became 999.99… g and was refused). `measurement_barcode_parser.rb` checked: it only multiplies `Rational` by the integer factor and uses `Rational` prices, so it was already exact. Specs: 3 kg at 1/3 → 1000 g, 0.006 kg → 2 g, 7 l at 3/7 → 3000 ml, 6 cases at 1/6 → 1; 1 kg at 1/3 and 5 cases at 1/6 refused.
3. **Tracked-mode switch is store-wide** (`units_controller.rb`): requires the store default of traceability on (`FeaturePolicy.require_store!`), plus the existing `write_pos_topology` + `pos.topology.manage`. Spec: one branch off does not decide it; store off → 409; store on → 200.
4. **`closures_with_unexplained_variance`** (`operational_metrics.rb`): closures of the last 30 days (`closed_at`, existing `(branch_id, closed_at)` index) whose variance needed an approval (`|variance| > threshold`, or any variance without a threshold) and has none, or with an overage not yet fully reconciled. Approved shortages are explained. Spec: approved unreconciled overage counted, approved shortage not, a 40-day-old overage not.
5. **Indexes** — new migration `20261107180001_add_pos_operational_metrics_indexes` (applied to the **test DB**; **apply to dev**): partial `idx_pos_tender_attempts_unresolved (branch_id, created_at) WHERE status IN ('prepared','unknown')`, `idx_pos_outbox_undelivered (store_id, status, available_at) WHERE status IN ('pending','failed')`, `idx_pos_received_funds_held_cash (branch_id) WHERE kind='cash' AND custody='held'`. Held cash uses `NOT EXISTS` instead of `NOT IN`.
6. Low items:
   - Command log: commands run inside another command's transaction carry `parent` (spec: the draft created by an exchange logs `parent: exchange.execute` before the exchange's own line, which is written after its commit).
   - `lock_waits`: unavailable (not zero) when the role cannot see other sessions' wait columns; the age is labelled `oldest_waiting_statement_seconds` and measured from `query_start` of statements waiting on a lock, excluding the reader's own backend.
   - `FeaturePolicy.set!` authorizes before validating (spec: a cashier sending an unknown feature with no reason gets 403).
   - `Displays::Pairing.exchange` refuses (same 404 `pairing_invalid`) when the display is off at the session's branch; switching the display off (store or branch) spends every open pairing code there.
   - A completion refused with `feature_disabled` releases the workspace's credit reservations and revokes their approvals (`credit.release`, reason `feature_disabled`) instead of holding exposure until expiry.
   - Outbox figures (store-wide) only for `write_pos_topology` holders; `null` for branch readers.
   - `key_digest` is an HMAC with a secret derived from `Rails.application.key_generator` (`spree.pos.command_log.key_digest`).
   - The payload `branch_id` is logged only when it is a branch of the command's store (spec: a foreign branch id never reaches the log).
7. **Replay of a committed draft-create** (`command_executor.rb` `replay_authorize:`, `workspaces/create.rb`): when the actor holds a receipt for the key with the same payload, the stored result is returned if the actor is still an active member of the draft's branch with `write_pos_orders`, before the open-shift check (never before the membership check). `full_retail_spec` now replays all 52 commands including draft creates after the shift closed, and refuses the draft replay once the cashier's membership is disabled.
8. **Test quality** (`security_spec.rb`, `feature_flags_spec.rb`):
   - IDOR writes: each write first by the outsider (403/404, state unchanged — return count, refund approval, lease holder/generation/editor, display generation, print count, shift count, export download audit; no download URL in the body), then the insider's identical request must succeed (2xx) and change that state.
   - Cookie origin: a foreign-origin refresh and logout now get 403 with no token, no rotated cookie and no new refresh token; the same cookie refreshes from the app's own origin. This needed a **fix**: Spree's refresh/logout accepted the cookie from any origin and returned a fresh access token in the body (only CORS hid it from the caller's script). New `config/initializers/staff_session_origin.rb` (Rack middleware) refuses POSTs to `/api/v3/admin/auth/{refresh,logout}` whose `Origin` is neither the app's own host nor a `Spree::AllowedOrigin`; requests without `Origin` pass. The POS dev server proxies `/api` with the browser's `localhost` origin, which matches the API host, so it keeps working.
   - Replay while off for every gated family: credit approval, credit request and completion on credit; return prepare; refund request; exchange; opening balance; display pin; cash movement request; export create (HTTP 202 with the first export, no second row).
