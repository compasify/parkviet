## What was built

Backend (`server/`):

- Migration `20261107170000_create_spree_pos_receipt_displays` (applied to the **test DB only**): `spree_pos_receipt_snapshots` (one per source document, unique `(source_type, source_id)` and `(store_id, source_type, number)`, source type check), `spree_pos_receipt_prints` (copy number 0 = original, unique per snapshot), `spree_pos_display_sessions` (token digest unique, one live session per shift, generation >= 1, attempt pin needs an order pin), `spree_pos_branches.display_freshness_ttl_seconds` (nullable, 5..120).
- `ReceiptSnapshot` (read-only once persisted) and `ReceiptBuilder`: built inside the posting transaction of the sale completion, return receipt, refund payout confirmation and shift close (`ReceiptBuilder.issue!`, idempotent per source). Sale payload: lines with sale unit, base-unit conversion text (unit names copied at issue time), unit price, line discount and net amount, per-line traceability, totals with discount and both tax totals, receipts by method from the sale's own allocation children (cash handed and change, masked bank reference), paid total, approved debt and due date from the receivable debit, note, cashier, branch/register names. Return slip: returned lines/condition/value, credit note and refund entitlement only when the entitlement is posted (otherwise "pending"). Refund slip: method, amount, masked reference. Closing slip: float, inflow/outflow, expected, counted, variance, closer/approver, breakdown. Header text "Phiếu bán hàng POS — không phải hóa đơn điện tử" is served as `disclaimer`.
- Sources that are not posted have no receipt (`409 receipt_unavailable`). A posted source without a snapshot (posted before this phase) gets one on first lookup marked `issued_late: true`.
- `GET /pos/receipts?branch_id&number[&source_type]` (search, active members of the branch only), `GET /pos/receipts/:id`, `GET /pos/receipts/lookup?source_id=<workspace|return|refund|closure id>`, `POST /pos/receipts/:id/prints` (idempotency key; first print original, later prints numbered copies labelled `BẢN SAO`; audit `receipt.print` / `receipt.reprint`; no Payment, stock movement, order, funds or cash movement). Customer name masked (initials) unless the reader holds a contact capability at the branch (same set as receivables); phone always masked.
- `DisplaySession` + workflows `displays/bind.rb` (bind or rebind to the caller's own open shift; token 32 random bytes, SHA-256 digest at rest, 12 h TTL, rotation on rebind drops pin and acknowledgement and increments the generation; the plain token is only in the bind response and is never stored in a command receipt), `displays/pin.rb` (pin order / pin order + prepared bank attempt / clear, through `CommandExecutor` with idempotency keys; every pin and clear increments the generation; another customer needs `ack_current`), `displays/revoke.rb` (`ended` or `unresponsive` override; audited), `displays/guard.rb`.
- Cashier routes: `POST /pos/display_sessions`, `GET /pos/display_sessions/current?shift_id`, `GET /pos/display_sessions/:id`, `POST /pos/display_sessions/:id/{pin,clear,revoke}`.
- Public display channel `Spree::Pos::DisplayViewsController < ActionController::API`: `GET /api/v3/pos_display/state` and `POST /api/v3/pos_display/ack`, outside the Admin API, token only in `Authorization: Display <token>`; `Cache-Control: no-store`, `Pragma: no-cache`, `Referrer-Policy: no-referrer`, `nosniff`. Unknown/expired/revoked token, closed shift or staff no longer active at the branch all give the same 401. `DisplayState`: per-read sequence (`UPDATE … RETURNING`, also `last_seen_at`), signed lease (`message_verifier`, bound to session id + generation + issue time, expires with the freshness window), pinned order lines/totals/paid/amount due, and for a pinned bank attempt still `prepared` the amount, transfer note (order number) and the account text of the store's configured bank payment method description (HTML stripped). No customer, staff, debt or balance fields.
- ACK: accepted only for the current generation with a valid lease of the same session; `acked_at` stores the lease issue time, so an acknowledgement is only as fresh as the state it proves. `ack_current` = current generation and `acked_at` within the window.
- Branch setting `display_freshness_ttl_seconds` through `PATCH /pos/branches/:id` (nil = default 15 s; must be accepted in device UAT).

Frontend (`apps/pos/`):

- `lib/display-generation.ts`: freshness state machine. Deadline = request send time + window on `performance.now()`; renewal only by a response that is the latest request, has a higher server sequence and a generation not older than the current; hide at once on offline, page hidden, resume (wall clock jumped ahead of the monotonic clock, `pageshow` persisted, `resume`/`freeze`) and deadline; responses to requests sent before a hide are ignored; `pinDecision` mirrors the server gate.
- `pages/customer-display.tsx` at `/pos/display` (outside the staff session): token from the cashier window via `postMessage` (origin and opener checked) or typed pairing code, kept in this tab's `sessionStorage`; polls about three times per window, acknowledges after each fresh state, shows "Đang cập nhật…" with nothing else when not fresh, payment block only when fresh; 401 clears the token.
- `hooks/use-display.ts` + `components/display-pin-control.tsx` in the checkout panel: connect, freshness line (pinned order, confirmed/unconfirmed generation, polled every 3 s), "Hiện đơn này cho khách", "Hiện chuyển khoản …" for each prepared bank tender, clear with the warning that a photographed account/QR can still receive money and that late transfers go to the original order's unallocated funds, "Màn hình khách không phản hồi" (revoke `unresponsive`) when the clear is unconfirmed, open display window, reconnect (rotate), disconnect, pairing code shown only from memory right after binding. Tab switches never call pin.
- `lib/print-adapter.ts` (format/deliver interface, browser implementation only): `formatReceipt` (no amount computed client-side), `formatPrebill` ("TẠM TÍNH – CHƯA THANH TOÁN", no number), `createBrowserPrintAdapter` (sets `@page` 80mm/A4, marks the paper on `<html>`, calls `window.print`, reports blocked/failed without side effects). `components/receipt-sheet.tsx`, `styles/receipt.css` (Vietnamese font stack, tabular numerals, 80mm and A4, print-only root).
- `pages/receipt.tsx` at `/pos/receipts?source=…|receiptId=…`: lookup, number search in the selected branch, paper choice (remembered), print = record the print on the server first, then print the sheet with the recorded original/copy label; when recording fails nothing is printed. Links: payment panel after completion, order detail, received return, confirmed refund, just-closed shift, menu.
- `components/prebill-dialog.tsx`: "In tạm tính" in the order menu.
- Scanner: `lib/scanner-calibration.ts` (per-register calibration in local storage: terminator Enter/Tab, max gap 30–300 ms, recorder from one test scan), `components/scanner-calibration.tsx` (dialog from the menu, `useScannerCalibration`), `createScannerKeyBuffer` takes the terminator; the workspace scanner uses the register's calibration. Existing guards stay: no capture in text fields or during IME composition, scans bound to the active workspace at enqueue time, unknown outcomes retried with the same intent and key, scale labels read by the server parser.

## Traceability integration point

`ReceiptBuilder#trace(sale_line)` (`server/app/services/spree/pos/receipt_builder.rb`) reads `Spree::Pos::TraceAllocation.sold` (statuses committed/consumed) of the sale line with `serial_unit` and `inventory_lot`, guarded by `defined?(Spree::Pos::TraceAllocation) && TraceAllocation.table_exists?`, and falls back to the sale line's own `serial_codes` / `lot_code` / `expiry_on`. Each row prints `serial`, `lot_code`, `expiry_on`, `quantity`. The receipt is issued at the end of `Workspaces::Complete` after `Inventory::AllocateTraceability.commit!` (already in that workflow), so committed allocations are present. To wire it once both are done: drop the `defined?`/`table_exists?` guard, and add a request example that completes a serial- and a lot-tracked sale and asserts `document.lines[].trace`. No trace data is invented anywhere; the frontend formatter prints whatever the snapshot carries.

## Decisions and deviations

- The display ACK is `POST /api/v3/pos_display/ack` on the public display controller, not an admin `display_sessions/acknowledgements_controller.rb`: the display holds no staff session, so an admin route could not authenticate it.
- Receipts are issued in the posting transaction; a receipt failure would roll the posting back (it is part of the posted document). Printing is a separate, idempotent command and can never undo anything.
- Bank QR: there is no structured receiving-account configuration (bank BIN/account/holder) in the repo, only the core payment method. The display therefore shows the configured payment method's description as account text and never a QR; with no description it asks the customer to ask the cashier. A VietQR/EMV adapter needs structured account config and is future work; nothing auto-confirms.
- The plan listed `apps/pos/docs/device-uat.md`; as instructed it is `reports/device-uat.md`.
- Freshness default 15 s is applied but documented in the UAT template as needing merchant acceptance; there is no topology editor field for it yet (set through `PATCH /pos/branches/:id`).

## Sửa sau review

Decisions applied: issuing a receipt never blocks or rolls back a posting; a late-posted return entitlement gets a supplementary slip; closing slips only for closer / variance approver / `pos.report.read`; return and refund slips per `Masking.returns_visible?` at the receiving or the sale branch; an original consumed by a failed print is accepted and the error says the next print is "BẢN SAO"; separate devices pair with a short single-use code; strict offline on the display.

### Backend

1. **Per-type receipt authorization** (`receipts_controller.rb`, rewritten): `readable?(type, record)` — sale: active member of the sale branch; `return`/`return_supplement`: `returns_visible?` at receiving or sale branch; `refund`: same with the return's sale branch; `shift_closure`: active member and (closer, variance approver, or `pos.report.read`). Used by `show`, `lookup` (before any lazy issue) and `prints` (also inside the command's authorize). `index` lists only visible types for the branch (sales; return documents with return rights there; closing slips closed/approved by the reader, all of them with report rights). `ReceiptSnapshot#source_record` resolves the source.
2. **Pin/clear compare-and-set**: `expected_generation` is required (409 `generation_required` when missing), part of the idempotency payload, compared under the session row lock; mismatch → 409 `generation_stale` with `current_revision`.
3. **Issuance never blocks posting**: `ReceiptBuilder.issue_safely!` wraps `issue!` in a savepoint, reports any `StandardError` with `Rails.error.report(handled: true)` and returns nil; the four posting hooks use it. The next lookup issues the slip `issued_late`. `RecordNotUnique` now looks the snapshot up by source and re-raises when the clash was on the document number (reported by `issue_safely!`). **Supplementary slip**: `ReturnOperation` entitlement posted after its slip (`ApplyCreditNote.post!`, used by the cancel / predecessor path) → `ReceiptBuilder.issue_supplement_safely!` issues `return_supplement` (number `<return>-BS`, "PHIẾU BỔ SUNG TRẢ HÀNG", posted credit note / refund entitlement) only when a `return` slip exists with `entitlement_posted: false`; the original slip is untouched.
4. **Print replay**: the command result stores only `print.to_pos`; the receipt is rendered after the executor with the current reader's masking.
5. **N+1**: `DisplayState` preloads sale lines; receipt index preloads `max(copy_number)` per page (`to_pos(copies:)`); sale traces are loaded once per receipt (`TraceAllocation.sold … group_by(sale_line_id)`).
6. **Pairing**: migration `20261107170001_add_pos_display_pairings_and_receipt_supplements` (test DB only): `spree_pos_display_pairings` (code digest unique, `expires_at`, `used_at`, creator) and `return_supplement` in the snapshot source check. `DisplayPairing` (8 chars from a 31-character alphabet without 0/O/1/I/L, 10-minute TTL, SHA-256 at rest), `Displays::Pairing.issue` (`POST /pos/display_sessions/:id/pairing_code`, owner only, spends earlier codes, audited, `no-store`) and `.exchange` (`POST /api/v3/pos_display/pair`, unauthenticated, single use, rotates the session token, audited `display.paired`; unknown/used/expired/revoked all 404 `pairing_invalid`). Rate limit: Rails `rate_limit` 10 attempts per minute per client address (Solid Cache in production, a process-local store where the app cache is a null store), 429 `pairing_rate_limited`. Bind and revoke spend open codes. `DisplaySession#rotate_token!` is shared by bind and exchange.
7. **Trace wired**: `ReceiptBuilder#trace` reads committed/consumed `TraceAllocation` rows directly (guard removed), falling back to the sale line's own codes only for lines without allocations.
8. Low: no POS ledger uses database triggers, so none was added for snapshots (model `readonly?` as elsewhere). State reads and acknowledgements have no rate limit beyond the token's scope (one open shift, 12 h) — documented in the controller.

Specs added to `receipts_displays_spec.rb` (now 19): reader matrix (member without return rights refused on lookup/show/print and absent from index; sale-branch return staff read a slip received elsewhere; non-closer manager refused a closing slip and does not list it; report reader allowed), builder failure leaves sale, return, refund payout and shift close committed and reported, then the lookup issues `issued_late`; supplementary slip after a predecessor is canceled; serial + lot traces (`IMEI-2`; FEFO lots `L-EARLY` 2 and `L-LATE` 1 with expiry); print replay keeps one print and re-masks; delayed pin/clear after a clear refused `generation_stale`, missing expected generation refused; pairing code (format, digest, no token in the cashier response, dashed lower-case accepted, old token stops working, single use, expiry, newer code spends older, revoke spends, rate limit 429).
